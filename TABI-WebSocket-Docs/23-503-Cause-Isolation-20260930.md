# 登録POSTの503原因特定（2026-09-30）

## 1. 結論

対象POSTを503にする直接の設定は、`/TABI/api/.htaccess` の管理API書き込み停止Rewriteである。確認できた設定・要求条件・応答を結び付けた原因特定であり、当時の本番Apacheのリクエスト単位traceを取得したという意味ではない。事業者の非公開設定や同時障害が一切ないことまでは保証しない。

**過去と現在を区別する。** 過去の実測は11:22:39 JSTの503と、その直後11:26の設定・11:26～11:28のRDS照合。今回は11:58:16 JSTに設定を新たに読み取り、同じ停止版ハッシュと条件が残っていることを確認した。現在も同条件のPOSTは設定上503になるが、本番POSTでの再現はしていない。

## 3. STEP 1：H1・H2の現在設定と適用順

確認時刻：2026-09-30 11:58:16 JST。既存の認証済み共有SSHからファイルを読み取った。基点は `/home/users/1/mond.jp-genshin`。実ファイルのrealpathも一致している。

通常と重複のindex.phpは両方実在し、別ファイル。通常経路と同じファイルだから安全、と推測したのではなく、重複入口を通常へ内部書き換えする14行と、その前の停止条件を確認した。

```apache
# /TABI/api/.htaccess 現在9～10行
RewriteCond %{REQUEST_METHOD} !^(GET|HEAD|OPTIONS)$
RewriteRule ^(?:api/)?Admin(?:/|$) - [R=503,L]

# 同14行
```

停止版SHA-256：`3afbbbb87ab7708d4e610faa8c311a4d86fc28bdb4aab4181f5edc2c22cf514b`。前回11:26に読み取った値と一致。ファイルmtimeは9月28日16:28:03 JSTだが、mtime単独では編集者・実際の切替時刻を証明しない。

処理の対応：

1. 対象の通常index.phpは実在する。確認した親の「存在しないパスだけのSPA fallback」による別URIへの誘導ではない。
2. apiディレクトリのRewriteで比較するパスは `Admin/index.php`。先頭のディレクトリ接頭辞を除いた形が正規表現に一致する。resourceのクエリはこのRewriteRuleのパス判定に含まれない。
3. POSTはGET／HEAD／OPTIONSのいずれでもなく、否定条件に一致する。
4. `[R=503,L]` が503を決定し、その後の登録PHPへ進めない。3xxのLocation redirectとしてブラウザを別の登録先へ移す処理ではない。
5. 重複経路では `api/Admin/index.php` が同じ正規表現に一致する。POSTは14行の入口統一より前に停止する。GETは停止条件に一致せず、14行で通常入口へ内部書き換えされる。
6. 先行調査のCookieなしGETは両経路とも401 JSON、正規管理者セッションのGETは一覧itemsを返した。GETが停止対象外であることと整合する。今回新しいGET／POSTを本番へ送って確認した結果ではない。

確認した.htaccessにErrorDocument指定はない。ロリポップの上位サーバー／VirtualHost設定は取得できず、2127 bytesのHTMLを選ぶ具体的なErrorDocumentの配置・内容は未確認。**503を設定する処理と、503用本文を表示する処理は別**。PHPログが見つからないことだけを登録PHP未到達の根拠にはしない。

## 4. STEP 2～3：PHP・DB・実行基盤

今回、本番 `api/Admin/index.php`、`includes/bootstrap.php`、`includes/http.php`、`services/notices.php`、`api/config/db.php` の読み取りハッシュをCRLF/LF正規化してローカルと照合し、5ファイルとも一致した。

- `noticeRequireAdmin()` は未認証401、権限不足・異なる送信元403、JSON形式違い415。共通respondは渡されたHTTPコードをそのまま設定する。401／403を503に変換していない。
- `api/Admin/index.php` の40行は入力検証422、56行は一般例外500。ブラウザNetworkで観測した実HTTP503を、フロント文言の付け替えだけでは説明できない。
- `api/config/db.php` の82～115行にはDB接続失敗を503 JSONへ変換する別経路がある。ただし今回のPOSTはその登録PHPを起動する前の停止対象。別のDB障害がないという保証にはしない。
- SQLエラーは登録処理へ到達してからの問題。今回の原因調査で追加SELECTをしても11:22時点の接続成否の証明にはならないため、RDSへの新しい接続・SQLは行っていない。前回の11:26～11:28の保存確認は過去の観測として保持する。
- 本番WebのPHP実行方式は今回特定していない。SSHから使用したphp8.3がCLIであることを根拠に、Webも同じ方式やPHP-FPMであるとは判断しない。
- 当該リクエストIDに対応する実行基盤ログ・待ち時間は未取得。H1で説明できるため、サービス調査やAWS接続へ広げない。

## 5. STEP 4～5：事業者・中継・旧フロント

H1で対象のメソッド・パスと503を説明でき、矛盾する応答証拠はない。事業者の同時アクセス制限履歴、障害記録、WAFログ、プロキシ／キャッシュ／Service Workerの実介入は未確認のままとし、否定に置き換えない。これらを追加調査するための管理画面操作やアクセスの繰り返しは行わない。

旧フロントの存在と入力内容は記録22の本番ファイル・Network・ユーザー提示Payloadから再利用した。旧フロントは**併存問題**である。仮に停止条件を通過してDB接続・正規認証が成功すれば、今回のPayloadはnoticeValidateで全ユーザー・push=true・空の開始終了日時が受理され、その後のrequestKey欠落でInvalidArgumentExceptionとなり、index.phpのcatchから**422**を返すコードである。実際に本番で422を発生させたのではなく、配備コード照合に基づく後続経路の判断。

targetIdは「全ユーザー」では不要なので、その欠落自体を今回Payloadの422原因にしない。「特定ユーザー」に変えてIDを欠けば別の検証422になる。Push ON／全ユーザーは限定テスト条件違反であり、PHP自体が必ず不正入力と判定する値ではない。空日時は7月の日付が送信されたことを意味しない。管理者1の正規認証・作成権限確認済みという状態は引き継ぎ、今回再ログインや権限変更を要求しない。

## 7. 運用上の理由

停止ルールのコメントはPHP／フロント切替中の旧形式書き込み防止を理由としている。[記録18](18-Production-Completion-Record-20260928.md)と[記録19](19-Limited-Notification-Diagnosis-20260928.md)には、Codexが承認済み停止・復旧方針に従い、限定テスト中断後にmaintenance版へ戻した経緯がある。その後、管理者1の認証は解決したが、他管理者・公開CLIを停止できないというユーザー回答があり、停止解除条件を満たしたとは扱っていない。

したがって、現時点では意図された停止が残っている状態であり、単に不要な誤設定として削除しない。ファイルmtimeは上記の通りだが、当時の切り替え操作の厳密な実行秒・OS監査ログによる操作者の証明は未取得。記録上の実施主体とmtimeを混同しない。

## 8. 最小の修正案・影響・確認方法（今回未実行）

503だけを変える最小差分は、将来の解除条件を満たしてから停止ブロックを無効化し、重複入口の統一・SPA・認証は維持すること。ただしこのブロックを外すと**管理API全体の書き込み**が通るため、限定1件だけの許可にはならない。今は実行しない。旧フロントと新PHPの不一致も残るため、停止解除だけで登録機能が直るとはしない。

限定例外が必要なら、その設計・差分・認証検証・承認は別工程。今回の原因調査では実装しない。

将来の変更後は、まず設定差分・通常／重複経路の読み取り・認証拒否・SPAを確認し、別途許可された限定POSTで初めて登録とDB保存を確認する。今回作った全ユーザー・Push ONのPayloadは再送しない。障害時は保存済みrequestKeyとIDを先に照合し、承認済み停止版へ戻す。データ削除・新規キーでの無条件再送はしない。
