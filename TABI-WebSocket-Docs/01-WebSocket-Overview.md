# WebSocketの概要と採用理由

## 1. WebSocketとは

WebSocketは、ブラウザやアプリとサーバーの間に接続を維持し、双方から任意のタイミングでデータを送れる通信方式です。

通常のHTTP APIでは、基本的にクライアントがリクエストし、サーバーがレスポンスを返します。一方、WebSocketでは接続後にサーバー側からクライアントへ更新を通知できます。

## 2. TABIでWebSocketを使う理由

TABIでは複数のユーザーが同じ旅行グループを利用します。そのため、あるユーザーの操作を他の参加者へすぐ反映したい場面があります。

例:

- チャットメッセージの受信
- 旅行計画やスケジュールの変更
- 候補地・宿泊先・しおりの更新
- メンバーのオンライン状態
- 管理画面における件数や状態の更新
- システムエラー件数のリアルタイム更新

HTTP APIだけでも一定間隔で再取得するポーリング方式は実装できますが、更新がない場合でも通信が発生します。WebSocketを使うことで、更新が発生した時だけ対象クライアントへ通知できます。

## 3. 異なるデバイスでもリアルタイム処理されるか

処理されます。

ただし、「端末同士が直接通信する」のではありません。各端末が同じWebSocketサーバーへ接続し、サーバーが更新を中継します。

```text
スマートフォンA
      │
      ├── WebSocket接続 ──┐
      │                    │
PC B ─┼── WebSocket接続 ──┼── WebSocketサーバー
      │                    │
タブレットC               │
      └── WebSocket接続 ──┘
```

ユーザーAが操作した場合の基本的な流れは次のとおりです。

1. ユーザーAの端末が既存APIへ保存リクエストを送る。
2. APIがDBへ保存する。
3. 保存成功後、WebSocketサーバーへ更新を通知する。
4. WebSocketサーバーが同じ旅行グループの接続へ配信する。
5. PCや別のスマートフォンがイベントを受け取って画面を更新する。

端末の種類は問題ではありません。次の条件が満たされている必要があります。

- 各端末がインターネットへ接続している。
- 各端末がWebSocketサーバーへ接続できる。
- 同じ旅行グループのルームへ参加している。
- 認証と参加権限の確認に成功している。
- ブラウザがバックグラウンド制限などで接続を停止していない。

## 4. WebSocketとプッシュ通知の違い

WebSocketとFCMなどのプッシュ通知は用途が異なります。

| 項目 | WebSocket | プッシュ通知 |
|---|---|---|
| アプリを開いている時 | 得意 | 利用可能 |
| アプリを閉じている時 | 基本的に届かない | 届けられる |
| リアルタイム画面更新 | 得意 | 画面更新用途には不向き |
| 通信経路 | 自前WebSocketサーバー | FCM/APNsなど |
| 主な用途 | 開いている画面の同期 | 端末へのお知らせ |

TABIでは、アプリ表示中の同期にWebSocket、アプリを閉じているユーザーへの通知にFCMを使い分ける設計が適しています。

## 5. 採用しなかった、または注意が必要な方式

### ポーリング

数秒ごとにAPIへ問い合わせる方式です。実装は比較的簡単ですが、更新がない場合もリクエストが発生します。

### ロングポーリング

サーバーが更新までレスポンスを保留する方式です。通常のポーリングより効率的ですが、接続管理が複雑になります。

### Server-Sent Events

サーバーからクライアントへの一方向通信です。双方向通信が必要なチャットや共同編集では、WebSocketの方が扱いやすい場合があります。

## 6. 結論

TABIのように複数ユーザーで旅行情報を共有し、表示中の画面を即時更新する用途では、WebSocketは適した選択です。

ただし、WebSocketはDB保存やプッシュ通知の代替ではありません。既存API・DB・FCMと役割を分担して使用します。
