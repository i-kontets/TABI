# TABI WebSocket 導入・実装ドキュメント

## 1. この資料の目的

この資料は、TABIでWebSocketを導入する際に検討・実施した内容を、別の担当者でも引き継げるように整理したものです。

単なるコマンド一覧ではなく、次の内容を含めています。

- WebSocketを選択した理由
- HTTP通信との違い
- 異なる端末間でもリアルタイム反映される仕組み
- インストールから実装までの流れ
- フロントエンド・WebSocketサーバー・既存APIの役割分担
- 実装時に間違えやすい点
- 接続できない場合の調査方法
- 本番環境で必要になる設定
- 運用・セキュリティ上の注意点

## 2. この資料で確認できていること

会話履歴から、次の方針は確認できています。

- TABIでリアルタイム処理を実現するためにWebSocketを使用する。
- 同じアプリを利用していれば、PC・スマートフォンなど端末が異なってもリアルタイム更新の対象にできる。
- リアルタイム処理は「同じ端末内だけ」で完結するものではなく、WebSocketサーバーを経由して各端末へ配信する。
- 接続中のユーザーだけでなく、切断・再接続も考慮する必要がある。
- WebSocketだけにデータを保持させず、正式なデータは既存DBへ保存する設計が必要である。

## 3. 現在の資料で要確認となる項目

今回参照できた会話履歴には、実際にインストールしたライブラリ名、WebSocketサーバーのファイル名、使用ポート番号、デプロイ先の最終値が残っていません。

そのため、以下は各ファイル内で `要確認` と記載しています。

- Socket.IO、ws、Ratchetなど、実際に採用したライブラリ
- WebSocketサーバーの起動コマンド
- 開発環境のポート番号
- 本番環境のドメイン・パス
- systemd、Supervisor、PM2などの常駐方法
- NginxまたはApacheのリバースプロキシ設定
- 認証トークンの具体的な受け渡し方法
- 実装済みイベント名

コードと設定ファイルを確認できた場合は、`要確認` を実値へ置き換えてください。

## 5. 最も重要な設計原則

1. DB保存を正とする  
   WebSocket通知が届いても、DB保存に失敗しているなら正式なデータとして扱いません。

2. WebSocketは更新通知に使う  
   画像・大量データ・全履歴を毎回WebSocketで送るのではなく、必要な識別子や更新内容を送ります。

3. 旅行グループ単位で配信範囲を分ける  
   全ユーザーへ一斉送信せず、`groupId` などを使って対象グループへ限定します。

4. クライアントから送られたIDを信用しない  
   ログインユーザーがその旅行グループへ所属しているか、サーバー側で検証します。

5. 再接続を前提にする  
   スマートフォンでは、画面ロック、通信切替、バックグラウンド移行により接続が切れます。

6. HTTPS環境ではWSSを使う  
   HTTPSページから暗号化されていない `ws://` へ接続すると、ブラウザに拒否される場合があります。
