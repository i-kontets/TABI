## 再利用する処理

`src/pages/Admin/Notices/NoticeForm.jsx` の通常登録操作から、`src/services/admin/notices.js` → 管理API client → `api/Admin/index.php?resource=notices` へrequestKey、targetId、push、公開期間を送る。

`noticeRequireAdmin()` はSession本人ID、active・未削除状態、admin_usersのadmin_levelを確認する。閲覧は1以上、登録等の書き込みは5以上であり、管理者roomに接続できることだけを登録権限の証明としない。

登録ハンドラ → `noticeCreate()` → 既存NotificationRepositoryによってadmin_notices・notifications・notification_recipientsを同一トランザクションで保存し、COMMIT後に `noticePublishRealtime()` → realtime.php → AWSのuser:{id}へnotification_createdを送る。Push OFFでも通知本体・宛先は作る。今回、NotificationServiceや別の通知サーバーを二重実装していない。既存のFCM処理は変更していない。

受信側は `UserRealtimeListener.jsx` のイベントから、通知一覧と `useUnreadNotificationBadge.js` がAPI再取得する。再接続・focus・表示中の定期取得も既存経路を使う。実ブラウザ受信を確認するまでは、実装確認だけでPASSにはしない。

限定テストは新しい有効な公開期間・特定ユーザーtargetId=2・Push OFFとする。requestKeyで保存結果を追跡し、notifications.target_idはユーザーIDではなく関連元notice_idという既存仕様を守る。保存成功後の外部送信失敗とDB保存失敗を区別する。

## 追加したローカルファイル

`deployment/notifications/publish_admin_notices.sh` を追加した。管理画面の実行ファイルパス欄から起動するための薄いシェル入口で、通知ロジックは既存PHPを再利用する。

必要な理由：本番env.phpはホスト名のないCLIでAPP_ENV未指定ならlocalを選ぶ。またロリポップのPHP直接指定はCGI版になる場合がある。SAPI=cliを要求する既存公開CLIを確実に呼ぶには、PHP実行ファイルとAPP_ENVを明示する入口が必要。

処理順：引数なしを確認 → 実行ファイル・ログ親ディレクトリを確認 → APP_ENV=aws → `/usr/local/bin/php8.3` で既存PHP起動 → Web公開外ログへ出力。引数から時刻や対象を変えることはできず、秘密値を保持しない。日本語コメントを追加済み。

検証：sh -n成功。ネットワークなしの使い捨てDockerでPHPをダミーに置き換え、継承されたAPP_ENV=localがawsになること、正しいPHP・スクリプトの組み合わせ、ログの権限600、終了コード保持を確認。引数付き呼び出しはPHPを起動せず拒否。DBへの接続・変更はない。
