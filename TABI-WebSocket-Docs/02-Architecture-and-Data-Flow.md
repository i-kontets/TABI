# アーキテクチャとデータフロー

## 1. 推奨構成

```text
React / PWA
  ├─ HTTP API通信 ─────── PHP API ─────── RDS
  │                            │
  │                            └─ 更新成功通知
  │
  └─ WebSocket接続 ───── WebSocketサーバー
                                │
                                └─ 対象ルームへ配信
```

TABIの既存構成では、React側がPHP APIを呼び出し、RDSへ保存する処理があります。WebSocket導入後も、この保存経路を基本的に維持します。

## 2. 各要素の責務

### React / PWA

- WebSocketサーバーへ接続する。
- ログイン情報や認証トークンを安全に渡す。
- 表示中の旅行グループに対応するルームへ参加する。
- サーバーからイベントを受け取る。
- 必要に応じて表示を更新、またはAPIを再取得する。
- 画面終了時にイベントリスナーを解除する。

### PHP API

- 入力値を検証する。
- ログインユーザーを確認する。
- グループ参加権限を確認する。
- RDSへ保存する。
- 保存成功時のみリアルタイム通知を発生させる。
- 保存失敗時はWebSocket配信を行わない。

### RDS

- 正式なデータを保持する。
- メッセージ、旅行計画、ユーザー、グループなどを永続化する。
- WebSocket接続が切れてもデータを失わないようにする。

### WebSocketサーバー

- 接続を受け付ける。
- ユーザーを認証する。
- `groupId` ごとに接続を管理する。
- 更新イベントを対象グループへ配信する。
- 接続・切断・再接続を管理する。
- 不正なルーム参加を拒否する。

## 3. 推奨データフロー

### 更新操作

```text
1. React
   POST /api/schedules/update

2. PHP API
   認証 → 権限確認 → RDS更新

3. PHP API
   更新成功

4. WebSocket通知
   event: schedule:updated
   groupId: 12
   scheduleId: 345

5. 同じgroupIdのクライアント
   イベント受信 → 表示更新
```

## 4. WebSocketへ直接DB更新を任せない理由

WebSocketイベントだけでDB更新を行う設計も可能ですが、既存APIと処理が分散しやすくなります。

分散すると次の問題が発生します。

- API経由とWebSocket経由でバリデーションが異なる。
- 認可処理が重複する。
- エラー処理が統一されない。
- どちらが正式な保存経路か分かりにくくなる。
- テスト対象が増える。

そのため、既存APIで保存し、WebSocketは保存後の通知に使う方針が安全です。

## 5. 全員配信ではなくルーム配信にする理由

TABIには複数の旅行グループがあります。すべての更新を全接続へ配信すると、他グループの情報が漏れる危険があります。

```text
悪い例:
全ユーザーへ schedule:updated を送信

良い例:
trip-group:12 の参加者だけへ送信
```

ルーム名の例:

```text
trip-group:12
trip-group:25
admin
user:101
```

## 6. イベントで送るデータ量

通知データは必要最小限にします。

```json
{
  "event": "schedule:updated",
  "groupId": 12,
  "scheduleId": 345,
  "updatedAt": "2026-07-15T10:30:00+09:00"
}
```

詳細データが大きい場合は、イベント受信後にAPIから再取得します。

## 7. 管理画面のリアルタイム反映

管理画面にシステムエラー件数などを表示する場合は、一般ユーザー向けルームと管理者向けルームを分離します。

```text
admin
admin:errors
admin:analytics
```

管理者ルームへ参加できるかは、クライアントから渡されたフラグではなく、サーバー側の権限情報で判断します。
